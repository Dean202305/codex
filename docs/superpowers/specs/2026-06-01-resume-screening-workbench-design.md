# 简历筛选工作台改造设计

## 背景

现有网页版按“文件路径、模型配置、预检、开始筛选”组织，岗位要求主要来自岗位说明书 Excel，结果页只显示进度、统计和日志。新的工作方式要求 App 内直接维护岗位要求，支持一次上传多个岗位的简历，并在结果页可视化筛选明细。

## 目标

本次改造把网页升级为本地工作台：

1. 先配置 API，再配置岗位和上传文件。
2. 岗位要求从外部岗位说明书切换为 App 内维护。
3. 岗位要求由两部分组成：所有岗位统一要求、多个岗位各自要求。
4. 支持批量上传简历或分析文档，按文件名岗位和岗位库匹配后筛选。
5. 结果页展示可筛选的分析结果表格，并支持下载本地 Excel。
6. 结果理由更详细，单独展示候选人优势点。

## 用户流程

1. API 配置
   用户填写 API 地址、API Key、模型名、超时时间、是否允许模型失败兜底。保存后可进行轻量检测。后续筛选默认优先使用模型。

2. 岗位要求库
   页面提供“所有岗位统一要求”编辑区，用于共性筛选条件，例如学历底线、地点、薪资范围、行业偏好、统一淘汰项。

   同一页提供多个岗位卡片，用户可新增、复制、删除岗位。每个岗位包含岗位名称、岗位别名、地点、薪资、经验要求、硬性条件、核心职责、能力要求、加分项、可放宽项、淘汰项。

3. 批量上传
   用户选择或拖拽多个简历文件。首版以本地 App/本机服务为边界，上传文件会保存到应用管理的导入目录，再由现有提取和筛选管线处理。支持 PDF、JPG、PNG、DOC/DOCX、PPT/PPTX 和其他可见普通文件。

   系统优先从文件名识别岗位、地点、薪资、姓名、工龄。岗位匹配多个岗位要求时按精确名称、别名、包含关系依次匹配。无法匹配岗位或文件名信息不足时仍提取正文，但分类为待人工二筛。

4. 筛选与结果
   运行页保留进度、停止任务、日志和统计。任务结束后进入结果表格。表格显示候选人、岗位、地点、薪资、工龄、分类、总分、岗位匹配分、优势点、详细理由、风险/缺口、缺失信息、重复标记、文件名。

   用户可在页面查看结果，也可以下载生成的 Excel。Excel 仍保留追加写入原结果模板的能力，同时提供本次运行结果下载。

## 数据结构

配置文件增加 `job_requirements`：

```yaml
job_requirements:
  common:
    title: "所有岗位统一要求"
    content: ""
  jobs:
    - name: "财务总监"
      aliases: ["财务负责人"]
      location: "北京"
      salary: "18-28K"
      experience: "10年以上"
      must_have: ""
      responsibilities: ""
      competencies: ""
      nice_to_have: ""
      flexible: ""
      reject_rules: ""
```

后端会把 `common` 和匹配到的岗位要求合并为模型输入。保留旧的 `job_book` 配置字段作为兼容，但新界面默认使用 App 内岗位要求。

## 后端接口

新增或调整接口：

- `GET /api/config`、`POST /api/config`：返回和保存 API、结果表路径、岗位要求库等配置。
- `POST /api/model/check`：对当前模型配置做轻量检测，超时或失败返回明确错误。
- `POST /api/uploads`：接收批量文件，保存到应用导入目录，返回文件列表。
- `GET /api/uploads`、`DELETE /api/uploads/{id}`：查看和移除本次待筛选文件。
- `POST /api/runs`：启动筛选，使用上传文件和 App 内岗位要求。
- `GET /api/runs/{run_id}`：返回进度、统计、日志和本次结果摘要。
- `GET /api/runs/{run_id}/results`：返回结果表格 JSON。
- `GET /api/runs/{run_id}/download`：下载本次结果 Excel。

## 前端结构

React 页面改为工作台布局：

- 顶部显示当前阶段和模型状态。
- 左侧为步骤导航：API 配置、岗位要求库、批量上传、筛选结果。
- 主区域根据当前步骤显示表单、上传队列、运行进度或结果表格。
- 结果表格支持分类筛选、岗位筛选、关键词搜索、下载按钮。

视觉风格保持本地效率工具风格：信息密度高、分区清晰、少装饰，重点突出模型状态、岗位要求完整度、文件队列和结果表。

## 模型输出要求

模型仍返回结构化 JSON。结果理由需要更具体：

- `strengths`：优势点列表，必须写出与岗位相关的证据。
- `screening_reason`：详细初筛理由，说明统一要求、岗位硬性项、匹配项和判断依据。
- `risk_notes`：风险或缺口。
- `missing_information`：需要人工补充确认的信息。
- `scores.job_fit`：岗位匹配分。

后端对模型输出做兼容解析：如果旧模型只返回 `screening_reason`，前端仍可显示；如果返回 `strengths` 和 `risk_notes`，结果页和 Excel 会单独展示。

## 错误处理

- API 配置不完整时不能开始筛选，除非用户显式允许无模型兜底。
- 模型检测失败给出可读原因，不清空已填内容。
- 上传文件解析失败时保留记录，分类为待人工二筛。
- 岗位未匹配时保留记录，分类为待人工二筛。
- 下载失败显示错误，不影响页面结果查看。

## 测试计划

- 配置保存/读取岗位要求库。
- 模型检测接口成功与失败。
- 批量上传接口保存文件并列出队列。
- 使用 App 内岗位要求生成筛选输入。
- 结果 JSON 和 Excel 下载接口。
- 前端构建通过。
- 回归现有 CLI/网页测试，确保旧命令行能力仍可运行。
